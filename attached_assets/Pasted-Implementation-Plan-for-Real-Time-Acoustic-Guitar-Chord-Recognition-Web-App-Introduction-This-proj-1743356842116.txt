Implementation Plan for Real‑Time Acoustic Guitar Chord Recognition Web App

Introduction

This project aims to build a web-based application that listens through the device’s microphone and displays the guitar chord being played in real time. The focus is on recognizing basic chords (major and minor triads) on an acoustic guitar with sufficient accuracy for casual jamming. To achieve low latency, the solution will emphasize local audio processing in the browser, using cloud processing only as an optional fallback. The application will be implemented with web technologies (for example, JavaScript/TypeScript for the front end) leveraging appropriate audio analysis libraries or machine learning frameworks. In the following sections, we outline the overall chord recognition approaches, the models/data available, the front-end and back-end design, performance considerations, and how the app can be expanded in the future.

Overview of Chord Recognition Approaches

Chord recognition from audio is a well-studied problem in Music Information Retrieval. Most modern chord detection systems are hybrid approaches combining signal processing and pattern recognition. In general, the task can be seen as two sub-problems: identifying which pitches are present at a given time, and then mapping those pitches to a chord label over time. Below is an overview of common approaches:

Signal Processing & Template Matching: A traditional approach is to compute a time-frequency representation (typically a Short-Time Fourier Transform to get a spectrogram) and derive a chromagram (12-dimensional pitch class profile) from it. Peaks in the chroma vector indicate which musical notes are sounding, and these can be matched against predefined chord templates. For example, if the chroma shows strong energy in pitch classes C, E, G, it would match a C major template. This method is straightforward and fast: many implementations simply apply a constant-Q transform or FFT to get the chroma, then perform template matching to decide the chord. Template-based methods (used in tools like Essentia or Librosa) work well for basic triads but may be less robust if there’s noise or overlapping tones.

Machine Learning with Sequence Models: More advanced systems treat chord recognition as a sequence labeling problem. They still start with spectral/chroma features, but instead of simple matching, they use a statistical model or classifier to predict chords. A common strategy is using Hidden Markov Models (HMMs) or Dynamic Bayesian Networks (DBNs) where the hidden state represents the chord and the observation likelihood is given by how well the audio frame’s chroma fits that chord. The HMM can enforce temporal smoothing (e.g. chords don’t jump arbitrarily every 10 ms) by modeling chord transitions. This was the basis of older research approaches (e.g. Sheh and Ellis 2003 used an HMM for chord segmentation). Similarly, support vector machines or other classifiers have been applied after extracting features. For example, Chordino, a Vamp plugin algorithm, uses an NNLS chroma (non-negative least squares chromagram) for frame-wise pitch analysis followed by a dynamic Bayesian network to infer chord sequences. These methods improve stability and accuracy by incorporating musical knowledge (e.g. likely chord progressions) but can be computationally heavier.

Deep Learning Approaches: In recent years, deep learning models have achieved state-of-the-art chord recognition accuracy. These models (often Convolutional or Recurrent Neural Networks) learn to extract chord-relevant features from the audio automatically. A notable example is the Madmom library’s chord detector, which uses a 3-layer deep neural network to compute a “chroma-like” feature from the spectrogram, and then a Conditional Random Field (CRF) sequence model to output chord labels. Other research has used CNNs to directly classify chords from spectrogram patches, or even treated it as a multi-label classification of notes present. Deep learning can capture subtler distinctions and complex chords better than rule-based methods. However, these models require large training datasets and can be demanding to run in real time on device. For our purposes (basic chords, acoustic guitar), a small neural network could be trained to recognize major/minor chords, or we might leverage a pre-trained model if available. We will weigh this option against simpler methods based on the trade-offs of accuracy vs. latency and complexity.


Overall, the recommended approach is to start with a robust but efficient method (such as chroma feature extraction + template matching or a lightweight classifier) and possibly integrate a sequence model to smooth the chord output. This should suffice for casual playing accuracy, while laying groundwork to integrate deeper learning if needed in the future. Indeed, research shows that after converting audio to a frequency-domain representation, what happens next (classification, smoothing) is crucial for chord detection accuracy.

Recommended Models and Datasets for Chord Detection

To build or train the chord recognition component, we can leverage existing models, libraries, and datasets from the MIR (Music Information Retrieval) community:

Existing Algorithms/Libraries: Instead of reinventing from scratch, we could use proven chord detection algorithms. For example, Essentia.js (a JavaScript port of the Essentia audio analysis library) includes algorithms for key and chord estimation. Essentia’s built-in chord estimator uses chroma features and template matching or pattern recognition to identify chords. This library, compiled to WebAssembly, is efficient and would run in the browser. Another option is to adapt Chordino or similar open-source algorithms (Chordino’s code is C++ for Vamp, but one could port its logic). If a machine learning approach is desired, we might use TensorFlow.js to run a small neural network model in-browser. There is no off-the-shelf TF.js chord model publicly known, but we could train one in Python (using TensorFlow/PyTorch) and then convert it to TensorFlow.js format. Notably, one project “autochord” provides a Python chord recognition library and even a JS demo app, which suggests it might be possible to reuse some model from there. For our needs, the simplest starting point is using a library like Meyda (a JS audio feature extraction library) to get a chromagram and then applying a custom chord logic, or using Essentia.js’s high-level chord detection if available.

Pre-trained Models: If we opt for deep learning, we should check if any pre-trained acoustic guitar chord models exist. While general music chord models (trained on diverse music) exist (e.g., models from the MIREX Audio Chord Estimation contests), their chord vocabulary and training might be overkill. An acoustic-guitar-specific model could be trained on isolated chords. There are some open datasets of guitar chord samples (for example, a Kaggle dataset of guitar chords audio, or the IDMT-SMT Guitar dataset with single notes and chords). In absence of a readily available pre-trained model for our exact use-case, using the simpler template method as a baseline is recommended and then gradually improving it (perhaps by training a custom model using a small curated dataset of guitar recordings).

Datasets for Training/Evaluation: Several public datasets can help develop and evaluate the system:

Isophonics & Billboard: These are well-known chord annotation datasets consisting of popular music (The Beatles, Queen, Zweieck in Isophonics; and hundreds of songs in Billboard). They provide ground truth chord labels for real songs. These datasets are used in research to train or evaluate chord recognition algorithms. However, they contain full mix audio (not just solo guitar) and include many chord types beyond just major/minor. They’re useful if we pursue a general chord model or want to evaluate how well our system performs on real music.

GuitarSet: This dataset specifically targets guitar playing. GuitarSet contains high-quality acoustic guitar recordings (360 excerpts) along with detailed annotations, including the chords that were intended and actually played. It covers various genres and playing styles on guitar, which is ideal for our app. We can use GuitarSet’s chord annotations to either train a model or to validate that our chord detection works well for solo guitar. Since it has both “instructed” chords (what the player was told to play) and “performed” chords (derived from transcription of the actual notes played), it’s very insightful for assessing casual playing accuracy (e.g., how often do players inadvertently fret extra notes, etc., and can our algorithm still label the intended chord).

Custom Chord Samples: We may gather a small collection of recorded guitar chords ourselves to fine-tune or calibrate the system. For instance, record each major/minor chord on a typical acoustic guitar, possibly at different strumming speeds or positions. This can help adjust thresholds for template matching or serve as training data for a machine learning model. Some community-driven datasets (like the Fabien Avinity’s Guitar Chords dataset on Kaggle, which includes recordings of chords like Am, C, Dm, G, etc., strummed in different ways) could be useful for this purpose.



Using these resources, our plan is to start with a heuristic/template approach (no training needed, just knowledge of music) and ensure it works reasonably for common open chords on acoustic guitar. Then, if higher accuracy is needed, we can explore training a small neural network on GuitarSet or similar data to better handle variations in timbre and chord voicings. We will validate the system on real guitar playing (possibly using a subset of the above datasets or new recordings) to ensure it meets the “casual playing” accuracy requirement.

Frontend Implementation Plan

The front end will be responsible for capturing microphone input, feeding it to the audio analysis pipeline, and displaying the detected chord name to the user. We will use standard web technologies (HTML, CSS, and JavaScript) for the UI. Key aspects of the front-end implementation include:

Microphone Access: Utilize the MediaDevices API to get audio from the user’s mic. The method navigator.mediaDevices.getUserMedia({ audio: true }) prompts the user for permission and, if granted, provides a live audio stream. This stream can be connected to the Web Audio API for processing. According to web platform documentation, getUserMedia() can capture the mic input which we then route into a Web Audio context for low-latency processing. We will ensure to handle permission prompts gracefully and notify the user if the microphone is not accessible.

Web Audio Pipeline (Browser): Create an AudioContext and attach the input stream to an AudioWorkletProcessor for analysis. The Web Audio API allows us to process audio data in real time on the client. By using an AudioWorklet, we can run custom audio processing code on a separate audio thread, keeping the UI responsive and achieving low latency. We will implement a custom AudioWorklet node (or use an AnalyserNode for simpler FFT approach) that receives chunks of audio and performs the chord detection (as described in the next section). The code to set this up will roughly be:

1. audioContext = new AudioContext();


2. source = audioContext.createMediaStreamSource(micStream);


3. audioContext.audioWorklet.addModule('chordProcessor.js'); (loading our processing module)


4. chordNode = new AudioWorkletNode(audioContext, 'chord-processor');


5. source.connect(chordNode); – The worklet will analyze audio; it may post messages back with detected chord info. We do not need to connect to audioContext.destination since we are not outputting sound, but just in case we might connect to a dummy destination or keep the node alive.



The chordProcessor.js Worklet script will contain the signal processing or ML inference code to identify chords (see next section for details). This design ensures minimal latency: the audio frames are processed directly as they come in, on a separate thread dedicated to audio, avoiding UI thread jitter.

User Interface and Display: The UI will simply display the current chord name prominently. For example, a text element that updates to “C Major” or “A minor” as chords are recognized. We might style this text to be large and centered for visibility. If needed, we can also show a small status indicator (like a colored dot) that goes green when the system is confident in a chord, or gray when no chord is detected (e.g., when not playing). For better user experience, we could include:

A visual indicator of input volume (like a simple meter) to reassure the user the mic is picking up sound.

Optionally, a scrolling display of the last few chords detected (forming a progression), which could be useful if someone strums a series of chords.

A toggle to switch between “local mode” and “cloud mode” (if we implement cloud processing as fallback).


Initially, to keep things simple, we will focus on a single chord label display that updates in near real-time as you play.

Front-end Framework/Tools: We can implement the above with plain JavaScript and the Web Audio API. However, using a framework like React or Vue is possible for structuring the UI. Given the simplicity of the interface (a couple of dynamic text fields and maybe some controls), a heavy framework is not strictly necessary. We might use lightweight state management to update the chord display when new data comes from the AudioWorklet (via chordNode.port.onmessage). We will also ensure the UI is responsive so that it works on desktop and mobile browsers (since mobile support is desired for future expansion). Using standard CSS or a library like Bootstrap/Tailwind could help make the interface adapt to different screen sizes.


In summary, the front-end will handle mic capture and user feedback. After setting up the audio context and analysis node, it will largely await results from the processing pipeline and update the display. This separation allows the heavy lifting to be done in audio threads or back-end, keeping the front-end logic straightforward.

Backend/Audio Analysis Pipeline

This section describes the core audio processing pipeline that will analyze incoming sound and determine the chord being played. In our architecture, this logic can be implemented in two ways: (1) as in-browser processing (via the AudioWorklet or JS code), or (2) as a cloud backend service (which receives audio data and returns chord results). We will prioritize the in-browser pipeline for real-time responsiveness, with the option to delegate to a cloud service if needed. Below is the plan for the audio analysis:

 Example of the chord analysis process. The left plot shows the waveform of an acoustic guitar strumming a chord. The middle image is a chromagram (time on horizontal axis, pitch classes C through B on vertical axis) showing the intensity of each musical note over time. Bright bands for C, E, and G indicate those notes are present strongly, corresponding to a C major chord. The system identifies and displays the chord as “C” (right), demonstrating real-time chord transcription from the audio.

Real-time Audio Processing Steps: The chord detection will operate on small frames of audio continuously. Here is a breakdown of the processing pipeline steps, which would be executed either in the AudioWorklet (for local processing) or on the server (if using cloud processing):

1. Audio Input Capture: The microphone input signal (a stream of 16-bit PCM samples, typically at 44.1 kHz or 48 kHz) is captured frame by frame. We will choose a frame size and hop size that balance latency and frequency resolution. For example, using ~2048 samples per frame with 50% overlap (hop ~1024) is a common setup, which at 44.1 kHz corresponds to ~46ms frames with updates every ~23ms. We might start with a frame size of 4096 (~93ms) to gather more frequency info for chord identification, then reduce if latency needs to be lower. The audio frames will be windowed (e.g., Hann window) to reduce spectral artifacts. If using the AudioWorklet, the process() method will supply input audio buffers of a certain length (128 samples by default in Web Audio API, but we can accumulate them into larger frames within the worklet as needed).


2. Spectral Analysis: For each audio frame, compute its frequency spectrum. The simplest approach is an FFT (Fast Fourier Transform) to obtain the magnitude spectrum. This yields the distribution of energy across frequencies. However, because music notes are logarithmic in frequency, we may instead use a Constant-Q Transform (CQT) which provides equal resolution per musical octave, or directly calculate a chromagram. Initially, we can use the FFT (which is readily available and fast) and then map it to a chroma vector. The mapping can be done by grouping frequencies corresponding to the same pitch class (e.g., sum or max the energy of all frequency bins corresponding to note C in any octave, do the same for C#, D, … B). Many implementations use a filter bank or peak picking to create a more robust chromagram (e.g., Harmonic Pitch Class Profile technique considers harmonic frequencies of notes). Libraries like Meyda or Essentia can directly output a chroma feature from time-domain audio, which we may leverage to avoid writing this completely from scratch.


3. Chroma Post-processing: The raw chroma vector might be noisy (due to overtones and noise). We will apply some smoothing or normalization. For example, we can normalize the chroma so that the largest value is 1 (since absolute amplitudes don’t matter for chord identity, just the relative presence of notes). We might also average the chroma over a short time (~100 ms) to account for the sustain of a guitar chord (when a chord is strummed, the notes ring out for a bit). This helps to stabilize the detection during the attack of a strum. The output of this step is a 12-dimensional feature indicating the strength of each semitone (C, C#, D, ..., B) in the current time window.


4. Chord Identification: Given the chroma vector, the system will decide which chord (if any) is being played. In the first version, we will target major and minor chords only (12 major + 12 minor = 24 classes). We will implement a template matching algorithm: each chord class has an ideal binary chroma template (for instance, C major ideally has 1’s for {C,E,G} and 0’s elsewhere). We compute a score for each chord, such as the dot product between the chroma vector and the chord’s template (possibly weighting or thresholding to account for partial matches). We can also consider inversions: a G major chord in first inversion (B-D-G) still produces a chroma with B, D, G which matches the G major template {G,B,D}. So template matching by pitch class inherently handles different fingerings/inversions of the same chord. We will pick the chord with the highest score. If that top score is below a certain confidence threshold, we can output “Unknown” or “No clear chord” (to avoid mislabeling random noise). In the future, if we include more chord types, we would expand the templates (for example, a dominant 7th chord template has four 1’s, etc.). For now, this simple rule-based classifier should work for basic chords. It’s essentially implementing musical knowledge directly. This approach has low computation cost – just a series of 12-dot-product comparisons on 12-element vectors each frame.

Machine Learning alternative: As an enhancement, we could train a classifier on the chroma vectors to decide the chord. For example, a small neural network that takes the 12-d chroma (or a concatenation of a few recent chroma frames) and outputs a probability for each of the 24 chords. Training data for this could come from synthesized chords or real recordings labeled with chords. A benefit of an ML approach is it might learn to ignore certain noisy aspects or give more weight to the root note, etc., potentially improving accuracy. But it introduces complexity (needing a training pipeline and to load model weights). Another ML approach is using a CNN on the spectrogram or a sequence model on the chromagram time series, but those are likely overkill for our scope. We note it here as a future possibility; initially the template method will serve as a baseline.



5. Temporal Smoothing: Chord changes on guitar typically occur on strum boundaries and last at least a fraction of a second. To avoid flicker in the displayed chord, we will apply smoothing to the sequence of detected chords. This could be as simple as requiring the same chord to be detected in say 3 consecutive frames (~100ms) before we confirm a change. Or we maintain a short memory of last N frames’ chord votes and take the majority. This prevents momentary misdetections from immediately showing up. (If we were to use an HMM/CRF, that would be a principled way to enforce temporal continuity, but we likely don’t need to implement a full HMM given performance considerations. For casual use, a simple debounce/average method works well to stabilize output.) The smoothing will introduce a tiny bit of lag in displaying a new chord (e.g. 50-100ms delay), but this is acceptable in exchange for a cleaner display that doesn’t flip rapidly between chords for a single strum.


6. Output/Display Update: Once a chord is determined for the current time, it is sent out of the analysis pipeline to the front-end UI. In the AudioWorklet scenario, the worklet can use this.port.postMessage({chord: currentChord}) to send the label to the main thread, where a handler will update the DOM. If we were using a back-end server, the server would send the results via a websocket or HTTP response to the client. The identified chord is then displayed to the user. This loop repeats continuously as long as audio is streaming.



The above pipeline will be implemented in JavaScript (within the AudioWorklet) for local processing. We will optimize the code to run efficiently (e.g., reuse arrays for FFT and chroma calculations to avoid excessive garbage collection that could stall real-time audio processing). The Web Audio thread can comfortably handle the lightweight math of an FFT and template matching within a few milliseconds per frame on modern hardware, which is well under the ~20ms budget for glitch-free audio.

Cloud Processing Option: In case the user’s device is too slow or for comparison, we will also set up an optional backend service. In this scenario, the front-end would periodically send audio data to a server (for example, posting a 1-second clip or streaming via websockets). The server (implemented in Python or Node.js) would run a more advanced chord recognition (it could use the same algorithm or a heavier deep learning model that might be too slow for the browser). Python is advantageous here due to libraries like librosa (for spectral features) and PyTorch/TensorFlow (to run a neural net model). For instance, a Python server could load a pre-trained deep learning model that recognizes chords and output more nuanced results. The server would return the chord labels back to the client which then displays them. This fallback mode would inherently have higher latency (network transmission and possibly processing time), so it might be an on-demand feature (e.g., user uploads a recording for analysis, or enables “high accuracy mode”). We will design the system such that the core logic is abstracted, and switching between local vs cloud processing is easy (perhaps determined by a config or user toggle).

In summary, the back-end audio analysis pipeline (whether running locally in the browser or remotely on a server) will use a frame-by-frame audio processing approach to detect chords. By using a chroma-based method with template matching, we prioritize simplicity and speed, which aligns with the requirement for real-time feedback. The approach leverages established signal processing techniques, and we cite known algorithms (like template matching and HMM smoothing from research) to justify our method. This pipeline is the “brain” of the chord recognition app.

Performance Considerations for Real-Time Processing

Ensuring the system works in real time is crucial. Here we address various performance factors and how we will handle them:

Latency: Our goal is to minimize the end-to-end latency from the moment a chord is strummed to when the chord label appears on screen. Using local in-browser processing avoids network latency completely, giving us an advantage over cloud-based solutions. The latency will mainly come from the audio frame size (e.g., a 50 ms frame introduces ~50 ms inherent delay) plus any processing time. We aim for total latency well below 200 ms (an average user will perceive under ~100–200 ms as near-instant for audio-visual response). By adjusting the frame/hop size, we can tune the latency vs. frequency resolution trade-off. If needed, we could use smaller frames (like 1024-sample ~23ms) at the cost of some chord clarity, but since chords sustain, a slightly larger frame is usually fine. We will test and choose a frame size that feels responsive yet accurate.

AudioWorklet vs Main Thread: To achieve stable real-time performance, the audio processing will run in an AudioWorklet thread, not on the main UI thread. This prevents UI activities (like DOM updates or other JS code) from interfering with audio timing. As noted, the AudioWorklet gives us a separate, high-priority thread with the ability to process each 128-sample tick within ~2.67ms on a 48kHz context. Our processing in each tick will be minimal (just buffering into our frame buffer). When a full frame is collected, we do the FFT and chord computation which might take a couple of milliseconds in optimized JavaScript. This should comfortably fit in the time budget on typical devices. We will also avoid any operations that could block or vary in time (no network calls or heavy memory allocation in the audio thread). The guidance from Mozilla’s real-time audio programming article will be followed: avoid dynamic memory allocation and complex logic in the tight audio loop.

Optimizing the DSP: We will use efficient algorithms for the spectral calculation. The FFT size we choose will be a power of two (for fastest computation using radix-2 FFT). We might use an existing FFT implementation (for example, the Web Audio API’s AnalyserNode performs an FFT under the hood; or use a library like fft.js or KissFFT compiled to WASM). Essentia.js, if used, has highly optimized DSP in WebAssembly which can significantly speed up feature extraction. Also, by focusing on 12-dimensional chroma (a very reduced representation), the later stages are trivial to compute. If we incorporate a machine learning model (like a small neural net) in the browser, we will use TensorFlow.js in WebGL or WASM backend for speed, and possibly quantize the model to reduce load. The TensorFlow.js team has demonstrated real-time audio classification in browser (e.g., detecting voice commands in real-time), which gives confidence that a lightweight chord model is feasible in JS. We will also keep the model small (a few tens of thousands of parameters at most) so that inference is a few milliseconds.

Memory and Garbage Collection: Real-time systems must be careful with memory to prevent GC pauses. In our implementation, we will allocate audio buffers and reuse them. For example, the array that accumulates audio samples for a frame will be a fixed-size Float32Array that we fill in circularly. We will avoid creating new arrays or objects on each audio callback. By following this pattern, we minimize garbage generation, and thus avoid unpredictable GC stalls on the audio thread. If using TF.js, we will use tidy() to dispose tensors promptly and reuse tensors for the model inference to avoid memory leaks.

Browser Compatibility: We will test in Chrome, Firefox, and Safari. AudioWorklet is supported in modern versions of these (Safari added AudioWorklet in Safari 14+). If a browser doesn’t support AudioWorklet, we have a fallback of using an older ScriptProcessorNode (though deprecated, it can be a fallback for compatibility). ScriptProcessorNode runs on the main thread, so performance may degrade, but for casual use it might still work on fast machines. We will note that the best experience is on browsers with AudioWorklet support.

Cloud Offloading Overhead: In the optional cloud processing mode, performance considerations include network latency and throughput. Sending raw audio continuously (PCM data) can be bandwidth-heavy, so if we implement this, we might compress audio (for example, send as Ogg Opus packets) or downsample to reduce bandwidth. The server should ideally maintain a low-latency connection (websocket) to stream results back. We must also consider that users on mobile networks might experience latency spikes that make cloud mode less “real-time.” Therefore, cloud mode might be used for batch processing (e.g., analyzing a recorded session) or when the user explicitly opts in despite potential delay.

Casual Accuracy vs. Performance Trade-off: Since we target casual playing (not pro studio precision), we can favor performance and simplicity over absolute accuracy. This means we might not attempt complex chord recognition that could slow things down. For example, we won’t analyze  polyphonic voicings beyond the basic chord tones, and we won’t try to differentiate nuances like C major vs C5 (power chord) in the basic mode. This keeps the computational problem simpler. In cases of ambiguous audio, the system might just choose the nearest basic chord, which is acceptable for a casual tool.

Testing and Profiling: We will profile the application on various devices (desktop with good CPU, mid-range smartphone, etc.) to ensure the processing loop keeps up with real time. If any bottleneck is found, we’ll optimize that part (for instance, using WebAssembly for the FFT or simplifying the algorithm). We’ll also monitor the audio callback timing; if the audio context’s callback seems to be lagging (indicating we’re doing too much work), we might reduce frame rate or complexity.


By adhering to these performance considerations, we expect to achieve a smooth real-time experience. The use of local processing, Web Audio API, and careful coding practices will ensure low latency audio analysis and chord display. The system will be designed to handle real-time input continuously without dropping frames or freezing the UI, which is essential for an interactive musical application.

Future Expansion Options

Once the basic version of the chord recognition app is running, there are several directions to enhance its capabilities. These include expanding the range of chords it can recognize, supporting different types of guitars and inputs, and making it available on more platforms. Key future expansions are:

Support for More Complex Chords: In the initial implementation, we focus on major and minor triads. A natural expansion is to detect additional chord types such as seventh chords (e.g. dominant 7th, major 7th, minor 7th), suspended chords (sus2, sus4), augmented/diminished chords, and perhaps power chords (5ths) commonly used on electric guitar. To support these, we would expand the chord template library or training dataset to include these categories. The detection algorithm might need to handle chords with four notes (for 7ths) or distinguish between say a major chord and a sus4 chord (which differ by one note). This can introduce ambiguity – for example, Csus4 (C-F-G) and Fsus2 (F-G-C) contain the same pitches; the system might need to use context or default to one naming. We can address this by perhaps detecting the bass note (if we have a way to pick out the lowest frequency, which often determines the chord inversion) or by user settings (e.g., an option to enable/disable advanced chords). Adding more chords will likely require more sophisticated logic or a learning-based approach to maintain accuracy. We would validate new chord type recognition with additional data (for instance, many 7th chords examples in GuitarSet, or recording some ourselves).

Electric Guitar and Other Instruments: Although the app is tuned for acoustic guitar, many users will want to use it with an electric guitar. Electric guitars can be used clean or with effects (distortion). A clean electric guitar signal (especially if directly input via an audio interface) should be similar to acoustic in terms of chord detection, though the timbre differences might require re-calibration (we might need to adjust frequency weighting since electric guitars might emphasize different overtones). Distorted electric guitar is trickier: distortion adds a lot of harmonic overtones, which can confuse chord detection (a simple power chord (root+5th) produces a full spectrum that might be misinterpreted as a major chord with added notes). In future, we could add a mode for “electric guitar (distortion)” where the algorithm expects that the input might be a power chord and tries to identify the two primary pitches (root and fifth) instead of labeling it as some random extended chord. We could also allow detection of common guitar techniques like palm muting (which might register as lower intensity in chroma) or implement a filter that detects a heavily distorted waveform and simplifies the chord logic accordingly. Another aspect is input method: electric guitar users might plug their guitar into the computer. We should ensure our app can take not only microphone input but also an audio interface line-in (which usually still appears as a microphone or audio source to getUserMedia if the interface is the system default input). As we expand to electric guitar, we would test with various scenarios (clean chords, distorted chords, different pickup settings) to see if the existing algorithm holds or needs retraining.

Mobile Porting and Platform Support: We want the application to be usable on mobile devices (phones, tablets) since many guitar players might use a phone to quickly identify chords. There are a few paths for this:

As a mobile web app: Modern mobile browsers do support Web Audio and microphone access. We will make sure the UI is touch-friendly (large buttons, etc.) and that it doesn’t require keyboard. iOS Safari and Android Chrome both allow audio capture, though iOS might suspend audio context when not in user gesture; we’ll handle that by starting audio in a user gesture (e.g., the user taps “Start” to initiate getUserMedia and AudioContext). Performance on mobile might be a concern; we will test and possibly reduce processing load (maybe use a smaller FFT or lower sample rate on mobile if needed). If the browser approach is insufficient, we could consider making a native mobile app. For example, using React Native or Flutter to reuse some code and embedding a WASM version of our analysis, or writing a native module in Swift/Kotlin that performs the chord detection. The plan would be to first ensure the web version is solid, then evaluate wrapping it as a Progressive Web App (PWA) so users can “install” it. A PWA would allow some offline use and a more app-like experience. We can also package the web app in a WebView inside a native app if distribution via app stores is desired. In any case, the architecture of separating UI and processing will help – we could reuse the core analysis logic (maybe as a WebAssembly module or a library) on different platforms.

Desktop Application: Although a web app can run on desktop in a browser, some users might want a standalone desktop app. Technologies like Electron could wrap our web app into a desktop application easily. This is a possible future step to make it more accessible as a tool.


Enhanced User Features: Beyond recognition, we can add features that add value to the user:

Chord Library/Diagram Display: When a chord is recognized, the app could display a guitar chord diagram (fingering chart) for that chord, helping beginners learn how to play it. We can have a small library of chord shapes and show the one matching the detected chord (assuming standard tuning).

Chord History and Export: The app could record the sequence of chords played in a session and allow the user to save it or export it (for example, to a text file or shareable format). This would turn it into a practice tool for songwriters to jot down progressions they just played.

Accuracy Improvements with Tuning and Calibration: We could allow the user to input their guitar’s tuning if they use alternate tunings, as this might affect the recognition (though our method is tuning-agnostic since it listens to sound, knowing the tuning could help constrain expected chords perhaps). We could also have a quick calibration where the user plays a known chord and the system adjusts (for instance, if the guitar is slightly flat, the chroma peaks might shift; an advanced version might do automatic tuning adjustment like some research suggests to account for slight detuning).

Extend to other instruments or audio sources: While guitar is the focus, the app could potentially work on ukulele or piano chords with some modifications. In the far future, broadening the scope could be considered (though distinguishing instrument-specific voicings might require instrument-specific models).



Each of these expansions can be tackled incrementally. The application’s modular design (separating front-end UI, audio capture, processing logic, etc.) will facilitate adding new features. For example, adding more chord types might just mean editing a config file of chord templates or plugging in a new ML model without changing the front-end. Supporting mobile might mostly involve refining the UI/UX and testing performance on those devices. We will also keep an eye on new web technologies – for instance, the Web Audio API might introduce new nodes or the Web Neural Network API (WebNN) might become available to accelerate ML in browsers; such developments could be incorporated to improve our app over time.
